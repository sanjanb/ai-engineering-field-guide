The **Domain Name System (DNS)** acts as the directory of the internet, converting human-readable domain names (such as `google.com`) into machine-readable IP addresses. Its hierarchical and decentralized design ensures high availability, speed, and resilience.

---

## 1. The DNS Server Hierarchy

DNS queries rely on two main functional tiers: **Resolvers** and **Authoritative Servers**.

| Server Level | Function & Key Details |
| --- | --- |
| **DNS Resolver** | A recursive server provided by your ISP or public services (e.g., Cloudflare `1.1.1.1`, Google `8.8.8.8`) that manages the resolution process on behalf of the client. |
| **Root Name Server** | 13 logical root server addresses worldwide. **Anycast routing** maps each logical IP to the nearest physical server node geographically. |
| **TLD Name Server** | Stores pointers to authoritative servers for specific extensions, including generic TLDs (`.com`, `.org`) and country-code TLDs (`.uk`, `.de`). |
| **Authoritative Name Server** | Holds the definitive mapping records for a domain. Managed by domain registrars or cloud providers like AWS Route 53 and Cloudflare. |

---

## 2. Step-by-Step Resolution Flow

When a user opens a web page like `google.com`, the lookup moves through local caches before querying external servers:

```text
[ Client Browser ]
        │ (1. Check Cache)
        ▼
[ Operating System ]
        │ (2. Check OS Cache)
        ▼
[ DNS Resolver ] ────── (3. Cache Hit?) ──────► Return IP to Client
        │ (Cache Miss)
        ├─► 4. Query Root Server  ────────────► Returns .com TLD Server IP
        ├─► 5. Query TLD Server   ────────────► Returns google.com Authoritative Server IP
        └─► 6. Query Authoritative Server ────► Returns target IP Address
```

1. **Browser & OS Cache:** The request first checks local memory in the browser and operating system.
2. **Resolver Query:** If un-cached, the OS issues a recursive query to the DNS Resolver.
3. **Root Server Request:** The resolver queries a Root Server, receiving the IP of the appropriate `.com` TLD server.
4. **TLD Server Request:** The resolver queries the TLD server, receiving the IP of the domain's Authoritative Server.
5. **Authoritative Server Request:** The resolver asks the Authoritative Server for the record and receives the target IP address.
6. **Response & Caching:** The resolver returns the IP to the client and caches it locally based on its **TTL (Time-To-Live)**.

## 3. High-Traffic Production Gotchas & Best Practices

Updating DNS records for live production environments carries risks due to **DNS propagation delays** and aggressive client caching.

### Common Risk Factors

* **Long Default TTLs:** Downstream resolvers cache old IPs for the full duration of a record's TTL.
* **Non-Compliant Resolvers:** Some ISP resolvers ignore TTL limits and keep stale IPs cached beyond their expiration time.

### Zero-Downtime DNS Change Strategy

1. **Preemptively Lower TTL:** Lower the TTL of the target record to a short window (e.g., `60 seconds`) several days prior to the update.
2. **Execute Record Change:** Update the record to point to the new server IP.
3. **Graceful Decommissioning:** Keep the old server running until traffic metrics show zero incoming requests.
