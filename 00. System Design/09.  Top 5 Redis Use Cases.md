## What is Redis?

Redis (Remote Dictionary Server) is an open-source, in-memory data structure store. It serves as an ultra-fast database, cache, and message broker supporting data structures such as **Strings**, **Hashes**, **Lists**, **Sets**, and **Sorted Sets**.

## Overview of Use Cases

```text
                      Top 5 Redis Production Use Cases
                                       │
     ┌───────────────┬─────────────────┼─────────────────┬───────────────┐
     │               │                 │                 │               │
  Caching      Session Store   Distributed Locks   Rate Limiter    Leaderboards
```

### 1. Distributed Caching

* **How it works:** Frequently accessed objects or database query results are stored in Redis RAM to bypass heavy database disk read operations, reducing application response times.
* **At scale:** Large clusters use **sharding** to distribute caching workloads. Key considerations include setting appropriate Time-To-Live (TTL) policies and preventing *Thundering Herd* cache stampedes.

### 2. Session Store

* **How it works:** Centralizes user session data across stateless application servers. Upon login, session state is written to Redis and a unique session ID is returned as an HTTP cookie.
* **Persistence & Failover:** Because RAM is volatile, pure disk snapshots (RDB) or Append-Only Files (AOF) can take too long to reload during a crash. Production session stores rely on **primary-replica replication** for near-instant automatic failover.

### 3. Distributed Locks

* **How it works:** Coordinates mutual exclusion across multiple application instances sharing critical resources using atomic commands like `SETNX` (*SET if Not eXists*).
* **Execution Flow:**
1. Client 1 executes `SETNX key value EX timeout`. If successful (`1`), it acquires the lock.
2. If the lock key already exists (`0`), competing clients wait and retry.
3. Client 1 releases the lock by deleting the key upon completion.

* *Note:* Production systems typically rely on battle-tested libraries (such as Redlock) rather than raw scripts for full fault tolerance.

### 4. Rate Limiter

* **How it works:** Prevents API abuse by keeping atomic counters on incoming requests per IP address or User ID using the `INCR` command.
* **Execution Flow:**
* Incoming requests increment the counter for a given client key.
* If the counter exceeds the defined threshold, requests are rejected (HTTP 429).
* Keys automatically expire via TTL after a fixed window (e.g., 60 seconds) to reset limits.
* Can also support algorithms like sliding logs or leaky buckets.

### 5. Gaming Leaderboards

* **How it works:** Uses **Sorted Sets (ZSET)**, a native data structure where every unique item is mapped to a numerical score.
* **Performance:** Elements are automatically maintained in sorted order. Retrieving ranks, top $N$ players, or updating scores runs in $O(\log N)$ logarithmic time.
