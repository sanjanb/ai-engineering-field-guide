## 1. Noun-Based URIs & HTTP Verbs (CRUD)

A core rule of REST is that **resources should be identified using nouns, not verbs**. The operation to perform on that resource is determined by the **HTTP verb**.

| HTTP Method | CRUD Operation | Purpose | Example Endpoint | Idempotent? |
| --- | --- | --- | --- | --- |
| **GET** | Read | Retrieve resource representations | `GET /v1/products/123` | **Yes** |
| **POST** | Create | Create a new sub-resource | `POST /v1/products` | **No** |
| **PUT** | Update / Replace | Replace an existing resource completely | `PUT /v1/products/123` | **Yes** |
| **PATCH** | Partial Update | Modify specific fields of a resource | `PATCH /v1/products/123` | **No** (depends on spec) |
| **DELETE** | Delete | Remove a resource | `DELETE /v1/products/123` | **Yes** |

> **Anti-Pattern:** Using endpoints like `/getAllProducts` or `/deleteUser?id=5`.
> **RESTful Pattern:** Using HTTP methods over clean resource paths like `GET /products` and `DELETE /users/5`.

## 2. Statelessness & Scaling

One of the most critical properties of REST is **statelessness**:

* **Every request is self-contained:** The server does not maintain client session state across multiple calls.
* **Authentication Tokens:** Every incoming request carries all credentials (such as a JWT in the `Authorization` header) needed to process it.
* **Horizontal Scalability:** Because any server node can handle any request without relying on local session storage, web applications become straightforward to scale behind a load balancer.

---

## 3. Idempotency & Safe Retries

Understanding **Idempotency** is essential when designing reliable distributed systems:

* **Idempotent Action:** Making identical requests multiple times produces the exact same server state as making a single request.
* `GET`, `PUT`, and `DELETE` are inherently idempotent. Executing `DELETE /users/123` ten times results in user `123` remaining deleted.
* **Non-Idempotent Action:** Executing `POST /orders` five times will create five duplicate orders unless an explicit idempotency key is passed in the request header.
* **Retry Policy:** Clients can safely auto-retry failed `GET` or `PUT` calls on network timeouts, but retrying `POST` calls requires strict idempotency controls.

## 4. HTTP Status Codes

REST uses standard HTTP response status codes to communicate outcome states to clients:

```text
2xx (Success)      ──► 200 OK, 201 Created, 204 No Content
4xx (Client Error) ──► 400 Bad Request, 401 Unauthorized, 404 Not Found
5xx (Server Error) ──► 500 Internal Error, 503 Service Unavailable
```

* **2xx Series:** Request received, understood, and accepted.
* **4xx Series:** Client-side issue (e.g., malformed JSON syntax, invalid authentication).
* **5xx Series:** Server-side failure (e.g., database connection pool exhaustion). These are candidates for client retries.

## 5. Pagination & API Versioning

### Pagination Parameters

When an endpoint returns thousands of records, returning the entire dataset causes memory bloat and high network latency.

* **Limit & Offset:** `GET /v1/products?limit=20&offset=40` (Fetches items 41 to 60).
* **Cursor-based Pagination:** `GET /v1/products?starting_after=prod_xyz` (Prevents duplicate/missing items when new rows are concurrently inserted).

### API Versioning

Versioning prevents breaking existing client integrations when introducing structural API changes.

* **URI Path Prefixing:** Prefixing the version in the URI path (e.g., `GET /v1/users` vs `GET /v2/users`) is the most transparent and common pattern.
* **Header Versioning:** Sending custom headers like `Accept-Version: v2`.
