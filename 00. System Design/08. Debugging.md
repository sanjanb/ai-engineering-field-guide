
## The Debugging Mindset

Effective debugging requires discipline and mental clarity rather than random guessing:

* **Computers are logical:** Every bug has a rational explanation, even if it feels impossible to locate at first.
* **Stuck state is temporary:** Persistence paired with systematic isolation will eventually reveal the root cause.
* **Know your limits:** Recognize when you need to bring in someone with specialized domain expertise.
* **Prioritize by severity:** Not every minor defect justifies high engineering costs—accept that low-impact bugs may be deprioritized.

## A Systematic Debugging Process

```text
   ┌───────────────────────┐
   │ 1. Gather & Reproduce │ Collect logs, steps, & recreate in staging
   └───────────┬───────────┘
               │
       Can it be reproduced?
        ├─── YES ──► ┌─────────────────────────────┐
        │            │ 2. Inspect & Isolate        │ Use print statements & debuggers
        │            └─────────────────────────────┘
        │
        └─── NO  ──► ┌─────────────────────────────┐
                     │ 3. Trace & Hypothesis Cycle │ Trace call stack & add prod logging
                     └─────────────────────────────┘
```

### Phase 1: Gathering Details & Reproducing

* **Collect evidence:** Request screen recordings, exact step-by-step reproduction instructions, system logs, and raw error messages.
* **Isolate environment:** Replicate the conditions on a staging server. Isolating the environment to consistently reproduce the issue is half the battle.

### Phase 2: Investigating Reproducible Bugs

* **Execution timelines:** Add temporary print statements to build a chronological sequence of code execution and compare expected vs. actual values.
* **Debuggers & Introspection:** Utilize ecosystem-specific debugging tools (e.g., Erlang OTP introspection) to pause execution and inspect runtime memory states.

### Phase 3: Handling Hard-to-Reproduce Bugs

Intermittent issues often stem from production-level traffic load, race conditions, or specific client hardware configs:

1. **Trace backwards:** Start at the error line and trace up the call stack.
2. **Build a request timeline:** Follow one failed transaction through its complete lifecycle in the logs.
3. **Hypothesize & Deploy Logging:** Form a theory, add targeted logging code, deploy to production, and monitor until enough data accumulates to confirm or reject the hypothesis.

## Unsticking Yourself

When progress stalls entirely, leverage cognitive context switches:

* **Step away:** Take a walk, exercise, or sleep on it to allow background processing in your mind.
* **Rubber Duck Debugging:** Explain the code step-by-step out loud to an inanimate object (or write a draft email to a mentor). Explaining forces structured thinking and exposes flaws in your assumptions.
* **Pair debug:** Bring in a teammate for a fresh perspective on the code.
